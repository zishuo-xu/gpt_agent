# MyAgent 上下文设计与缓存工程

> 更新时间：2026-08-03
> 本文系统总结 MyAgent 的上下文组织方式、缓存命中率提升的完整演进（含实测数据）与设计原则。

---

## 一、核心思想

**上下文 = 稳定前缀 + 增量尾部。** 所有设计围绕一个物理事实展开：

> **prompt 缓存命中的条件：两次请求的前缀字节级一致。**
> 前缀中任何一个字节变化，都会让变化点**之后的所有内容**缓存失效、重新计费。

因此上下文设计的本质是：**把稳定的内容放在前面且保持字节不变，把变化的内容隔离在尾部，并让每轮新增量最小**。

四条设计原则：

| # | 原则 | 落地 |
|---|---|---|
| 1 | 稳定内容进 system，**会话内不变化** | 记忆类静态段会话内只构建一次 |
| 2 | 高频变化内容**移出 system** | todos 作为独立消息注入 messages 尾部 |
| 3 | 新增内容**只追加在末尾** | 消息历史天然追加；repo map 惰性生成后追加 |
| 4 | **每轮新增量最小化** | 工具输出截断、软遗忘、子代理只回流结论 |

## 二、上下文分层架构

```
┌───────────────────────────────────────────────────────┐
│ system（会话内字节级稳定）                               │
│  ├─ 基础系统提示（固定常量）                             │
│  ├─ 项目指令 AGENTS.md（首次构建缓存）                   │
│  ├─ 全局记忆 MEMORY.md（首次构建缓存）                   │
│  ├─ 项目记忆 conventions/pitfalls/decisions（同上）     │
│  ├─ 跨项目记忆标题索引（会话内生成一次）                  │
│  └─ 仓库签名地图 repoMap（探索后生成，60s TTL 重扫）      │
├───────────────────────────────────────────────────────┤
│ messages（前缀 = 上轮全部，只追加尾部）                  │
│  ├─ user / assistant / tool 历史                       │
│  ├─ 旧 tool 结果 → 软遗忘占位（保留最近 N 轮）           │
│  └─ todo 快照（动态注入，插在最后一条 user 之前）         │
└───────────────────────────────────────────────────────┘
```

### system 与 messages 的分工

- **system 只放低频稳定内容**：文件不变则字节不变；会话中 agent 写入记忆**不刷新**当前会话（下次会话生效）——参照 Pi 的 AGENTS.md 启动时加载。
- **messages 承担所有动态内容**：历史自然追加、todos 每轮更新、软遗忘替换旧工具输出。追加在末尾的内容变化**不影响它之前的前缀**。

## 三、缓存命中率提升的三阶段演进（实测）

### 阶段 0：发现问题（命中率 4%）

通过回放生产级会话 trace 逐轮分析请求前缀，定位到两个 system 内的变化源：

1. **「当前任务清单」todos 在 system 中**：agent 长任务中频繁调用 TodoWrite，每次更新 → system 一字节变化 → 其后的整个 messages 历史缓存全部失效。回放 34 轮请求，system 变了 5 次，**全部来自 todos**。
2. **跨项目记忆索引每轮重扫**：`prepare()` 每次都遍历所有项目目录，内容可能抖动，且是纯 IO 浪费。

### 阶段 1：todos 移出 system（4% → 66.4%）

- todos 改为**独立 user 消息**注入 messages，插在最后一条 user 之前——高频变化只影响尾部，system + 历史前缀完整命中。
- 跨项目索引**会话内只生成一次**（惰性缓存）。

### 阶段 2：记忆类静态段会话内固定（66.4% → system 唯一值 1）

- AGENTS.md / 全局记忆 / 项目记忆 / 跨项目索引在会话首次 `prepare()` 时组装一次并缓存，之后复用。
- agent 运行中写记忆**不刷新当前会话 system**（下次会话生效）。

| 阶段 | 第 2 轮命中率 | system 稳定性 | 额外收益 |
|---|---|---|---|
| 修复前 | **4%** | 每轮变化（todos） | — |
| todos 移出 system | **66.4%** | 低频变化 | — |
| 静态段固定 | **65.6%**（第 1 轮 **97.2%**） | **唯一值 1** | **跨会话缓存命中** |

**跨会话缓存是阶段 2 的意外收获**：system 彻底稳定后，不同会话之间共享相同的 system 前缀，DeepSeek 的全局缓存让**新会话第 1 轮就能命中 97.2%**（此前首轮必为 0%）。

### 结构上限概念

命中率存在理论上限：**稳定前缀 tokens / 本轮总 tokens**。每轮必然新增消息（工具结果、模型回复），新增部分无法命中。实测第 2 轮新增约占 1/3，所以 65.6% 已接近结构上限——要继续提升，只能**压缩每轮新增量**（见 §7）。

## 四、缓存工程细节

### 4.1 供应商差异

| 端点 | 缓存机制 | 应对 |
|---|---|---|
| DeepSeek / OpenAI 兼容 | **整段前缀自动缓存**（无显式标记） | 前缀稳定工程是唯一手段；system 稳定后跨会话也命中 |
| Anthropic | `cache_control` 断点，分块缓存 | system 块加 `cache_control: ephemeral`，最后一个工具定义同样标记 |

### 4.2 可度量

- 每轮请求记录 usage（`input / output / cached`）→ `cost_update` 事件 → 会话页显示"本轮缓存命中率"。
- trace 文件保存每轮完整 request，可离线逐轮分析前缀变化（定位缓存破坏源的标准手段）。

### 4.3 软遗忘的缓存代价（权衡）

软遗忘把早期 tool 结果替换为占位符——**消息内容变化会破坏从该点向后的缓存一次**。这是主动接受的权衡：省下的 tokens（历史大幅缩小）远大于一次性缓存损失，且被遗忘消息之后保持稳定，后续轮次继续命中。

## 五、上下文管理机制总览

| 机制 | 作用 | 缓存影响 |
|---|---|---|
| 记忆静态段会话内固定 | 记忆类内容字节级稳定 | ✅ 正向（前缀稳定） |
| todos 移出 system | 高频变化隔离到尾部 | ✅ 正向 |
| 软遗忘 | 旧 tool 输出占位，控制体积 | ⚠️ 每次遗忘破坏一次缓存（净收益为正） |
| 硬压缩 | 全对话 → 结构化摘要 | ⚠️ 压缩后缓存必然失效（预期行为，重新写缓存） |
| 子代理隔离 | 探索派生独立上下文，只回流结论 | ✅ 主上下文不被探索过程污染 |
| repo map 惰性生成 | 探索后生成签名地图，追加在末尾 | ✅ 追加不破坏既有前缀 |
| 工具输出截断 | 256 行 / 30KB，留头尾掐中段（head 58% / tail 32%），带续读提示 | ✅ 控制每轮新增量 |
| 多轮工具结果分页 | Read 用 offset/limit 分页续读 | ✅ 避免一次注入大文件 |

## 六、对照 Pi Coding Agent

**借鉴了什么**：

| 借鉴点 | Pi 的做法 | MyAgent 落地 |
|---|---|---|
| 前缀稳定工程 | skills 不注入前缀、动态内容追加消息侧 | todos 移出 system、静态段固定 |
| 启动时加载项目指令 | AGENTS.md 启动时加载，运行中不刷新 | 记忆静态段会话内只构建一次 |
| 缓存可度量 | cache-stats.ts 逐轮统计 miss 与成本 | 每轮缓存命中率显示 + trace 可离线分析 |

**保持的差异**：MyAgent 是全功能 monolith（权限引擎、审批、子代理、记忆、Web 监控台），Pi 是极简 harness；缓存优化借鉴其思想，但架构路线不同。

## 七、未来方向（继续提升命中率）

命中率 = 稳定前缀 / 本轮总量，前缀已稳定，剩下的是**压缩每轮新增量**：

| # | 方向 | 预期 |
|---|---|---|
| 1 | **工具输出截断调优**：按工具类型差异化上限（Bash 输出可更小、Grep 只留匹配行上下文） | 直接降低每轮新增，命中率再上一档 |
| 2 | **Lazy skills 渐进式披露**：能力包每轮只占一行，用到才加载（Pi 的做法） | 减少常驻体积，避免"不破坏缓存"地按需扩展 |
| 3 | **动态工具列表**：只注入启用/用到的工具 | 缩减 system 体积（注意固定启用集避免破坏缓存） |
| 4 | **软遗忘节奏调优**：保留轮数（当前 4 轮）与遗忘触发策略，在"体积 vs 缓存破坏"间找最优 | 长会话更优 |

## 八、结论

MyAgent 的上下文设计围绕一条主线：**让稳定内容字节级稳定、让变化内容隔离在尾部、让每轮新增最小**。三阶段演进把第 2 轮命中率从 4% 提升到 65.6%，并实现了跨会话缓存（首轮 97.2%）。这套方法论（分析 trace → 定位破坏源 → 隔离变化 → 实测验证）可复用于任何基于前缀缓存的 LLM 应用。
